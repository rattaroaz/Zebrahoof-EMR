================================================================================
ZEBRAHOOF EMR — CLEANROOM RECREATION SPECIFICATION
================================================================================

Purpose
-------
This document describes every user-facing feature, data structure, business rule,
API contract, and visual design token in the Zebrahoof EMR application so that
another implementation (any platform, any language) can achieve:

  • 100% functional recreation of described behavior
  • ≥90% visual reproduction of the described UI

Explicitly EXCLUDED from this spec:
  • Test projects, test harnesses, CI configuration
  • Logging frameworks (Serilog, OpenTelemetry, audit log infrastructure)
  • Build scripts and developer tooling except where they affect runtime behavior

The reference implementation is ASP.NET Core 10 Blazor Server + MudBlazor + EF
Core + SQLite/PostgreSQL + a local Ollama/Qwen engine. Recreate the BEHAVIOR
and UI described here; do not need to copy the stack.


================================================================================
1. APPLICATION OVERVIEW
================================================================================

Product name: Zebrahoof EMR
Tagline in app bar: "Zebrahoof EMR"
Logo: SVG at images/logo.svg (zebra/hoof branding), height 32px in app bar

Domain: Electronic Medical Record (EMR) for outpatient/clinic use.

Architecture pattern (reference):
  • Server-rendered SPA with real-time circuit (Blazor Server equivalent)
  • Single-page shell with client-side navigation between routes
  • Hybrid persistence:
      - In-memory singleton services hold clinical chart data (problems, meds,
        encounters, inbox, tasks, admin catalogs) synced to database on startup
        and on mutations
      - Direct database persistence for: Identity users, documents (binary),
        encounter local-AI messages, sticky notes, patient sticky notes, audit logs,
        user sessions
  • Dual auth state: server cookie session + in-app user context object for UI
    role display and location switching

Default dev URL: http://localhost:5222
Optional HTTPS: https://localhost:7177

Database file (dev): App_Data/zebrahoof.db (SQLite)
Production option: PostgreSQL when connection string configured

4. AUTHENTICATION & SESSION
================================================================================

4.1 Identity System
-------------------
ASP.NET Identity equivalent with these roles:
  Admin, Physician, Nurse, MA (Medical Assistant), Billing, Scheduler, Lab, Patient

Seed users (password for all: "password"):

  admin@zebrahoof.com        → Admin
  physician@zebrahoof.com    → Physician
  nurse@zebrahoof.com        → Nurse
  ma@zebrahoof.com           → MA
  billing@zebrahoof.com      → Billing
  scheduler@zebrahoof.com    → Scheduler
  lab@zebrahoof.com          → Lab
  patient@zebrahoof.com      → Patient

Password policy (intentionally minimal for demo):
  Minimum length 1, no digit/lowercase/uppercase/symbol requirements.

Lockout: 5 failed attempts → 15 minute lockout.

4.2 Login Flow (/login)
-----------------------
Form POST to /account/login (application/x-www-form-urlencoded):
  Username  — accepts username OR email
  Password
  RememberMe — checkbox ("on" or "true")
  ReturnUrl — hidden, default "/"

Error query params on redirect back to /login:
  ?error=invalid     — unknown account or bad password
  ?error=inactive    — account deactivated
  ?error=locked      — lockout active
  ?error=...         — display generic "Invalid username or password"

On success: redirect to ReturnUrl (default /).
On MFA required: redirect /mfa-challenge?returnUrl=...
Logout success: /login?logout=success

Login page links: Forgot Password, Register as Patient.

4.3 Cookie Configuration
------------------------
Auth cookie name: zebrahoof.auth
  HttpOnly: true
  Secure: true (in production)
  SameSite: Strict
  Absolute expiration: 12 hours
  Sliding expiration: DISABLED

ASP.NET session cookie: zebrahoof.session, 30 min idle.

Refresh token cookie: zebrahoof.refresh
  Value: base64("{sessionId}:{refreshToken}")
  HttpOnly: true

Session ID cookie: zebrahoof.session.id
  Value: session Guid string
  HttpOnly: false (needed for SignalR query param)

4.4 Idle Timeout Rules
----------------------
Non-admin users: 15 minute idle timeout
Admin / "System Administrator" role: 30 minute idle timeout

Idle measured via:
  • Cookie validation on each request (updates last activity claim)
  • SignalR SessionHub Heartbeat() every ~30 seconds from client JS
  • SessionService tracks LastSeenAt on UserSession entity

When idle expires:
  • SignalR sends ForceLogout("Session expired") to client
  • Session revoked with reason "idle_timeout"
  • User redirected to /login

When ≤2 minutes idle remaining: IdleWarning toast/message.

4.5 MFA
-------
TOTP authenticator app (Otp.NET equivalent).
Recovery codes supported.
Pages: /mfa-challenge (anonymous, during login), /mfa-setup (authenticated).
ApplicationUser.MfaSecret stored encrypted at rest.
SystemSettings.RequireTwoFactor exists in admin UI but is NOT wired to enforce
org-wide MFA (per-user TwoFactorEnabled only).

4.6 Authorization
-----------------
Global: all pages require authentication except explicitly anonymous routes.
Admin-only pages: /admin/sessions, /admin/audit-log ([Authorize Roles=Admin]).

Defined policies (exist but mostly unused in UI):
  ChartEditorPolicy  → Physician OR Nurse
  PrescriberPolicy   → Physician only
  BillingPolicy      → claim CanViewBilling=true (Billing + Admin roles)

Patient REST API:
  POST/PUT patients → Physician OR Admin
  DELETE patients   → Admin only
  GET               → any authenticated user

4.7 Blazor Auth Bridge
----------------------
After cookie login, map Identity user → in-app User object:
  Id, Username, FullName, Email, Role (UserRole enum), Department

AuthStateService (singleton):
  CurrentUser, IsAuthenticated, CurrentLocation (default "Main Clinic")
  AvailableLocations: ["Main Clinic", "South Branch", "West Branch"]
  Events: OnAuthStateChanged
  Methods: Login, Logout, SwitchRole (demo), SetLocation

4.8 Account Endpoints
---------------------
POST /account/login     — form login (see §4.2)
POST|GET /account/logout — sign out, revoke session, clear cookies → /login?logout=success
POST /account/refresh   — rotate refresh token; 200 OK or 401

4.9 Session REST (anonymous — demo/admin tooling)
-------------------------------------------------
GET /api/sessions/active  → { sessions: UserSession[] }
GET /api/sessions/count   → { count: number }

4.10 SignalR Session Hub
------------------------
Path: /hubs/session
Auth: required; connect with ?sessionId={guid} query param

Server methods:
  Heartbeat() — updates last seen, sends IdleTimeUpdated(idleSec, absoluteSec),
                IdleWarning if ≤2 min, ForceLogout + revoke if expired

Client must connect after login using session ID from cookie.

11. AI / LOCAL ENGINE INTEGRATION
================================================================================

11.1 Local engine (Ollama + Qwen)
------------------------------
Provider: local Ollama on loopback (http://127.0.0.1:11434)
Endpoint: POST /api/chat (Ollama native; no cloud xAI/Grok)
Auth: none (loopback only)
Default model: qwen2.5:7b
Timeout: 15 minutes (configurable)

The backend can download the official Ollama Windows/Linux archive, extract it
under App_Data/ai-engine/, start `ollama serve`, and pull the configured Qwen
model. Admin UI: /admin/local-ai and Settings.

Config (appsettings LocalAi):
  BaseUrl, Model, AutoStart, RequestTimeoutMinutes, EngineDirectory

No GROK_API_KEY. Clinical prompts must not leave the machine.

Request body (JSON, camelCase):
  {
    "model": "qwen2.5:7b",
    "stream": false,
    "messages": [ { "role": "system|user|assistant", "content": "..." } ]
  }

Response parsing: message.content (Ollama) or choices[].message.content (compat).

If the engine is not installed/running: return a user-visible error pointing at
Settings → Local AI (do not crash the app).

11.2 Send to local AI (Patient Chart Button)
----------------------------------------
Precondition: at least one of: documents with ExtractedText, problems, meds, allergies
Disabled after first successful send per patient per session.
Resets when document count for patient increases.

Builds plaintext payload:
  === PATIENT === (name, MRN, DOB, sex)
  === CURRENT LOCAL RECORDS ===
    Problems, Medications, Allergies (formatted lists)
    Latest Vitals (if any)
    Recent Lab Results (last 10)
    Immunizations
  === UPLOADED DOCUMENTS === (full ExtractedText per document)

Prompt: "You are reviewing a patient chart... Acknowledge receipt, then provide
  a brief (3-5 sentence) summary noting discrepancies between uploaded documents
  and current local records."

Shows success snackbar with counts. Marks AiSession.documentsSent[patientId]=true.

11.3 Update Records from local AI (Demographics Tab)
-------------------------------------------------
Gathers: problems, medications, allergies, all documents for patient
Sends prompt requesting JSON-only response (no markdown fences):

Schema:
{
  "summary": string,
  "problems": [{ name, icdCode, onsetDate, resolvedDate, status, severity, notes }],
  "medications": [{ name, dose, route, frequency, startDate, endDate, prescriber,
                    status, isHighRisk, isLongTerm, instructions, refillsRemaining,
                    daysSupply, pharmacy }],
  "allergies": [{ allergen, reaction, severity, status, onsetDate }]
}

Rules in prompt:
  • Return COMPLETE chart (full replacement, not diff)
  • Preserve existing unless documents contradict
  • Add only with explicit document evidence
  • Never invent ICD codes
  • ISO date strings YYYY-MM-DD

On success:
  • Replace in-memory clinical data for patient
  • Persist to DB (delete all existing problems/meds/allergies for patient, insert new)
  • Fire PatientDataChanged event for UI refresh
  • Show summary snackbar with before/after counts

Limits: max 18,000 chars per document, 60,000 total doc chars in prompt.

17.1 Patients — /api/patients
-----------------------------
GET /api/patients/
  Query: page (default 1), pageSize (default 10), search (optional)
  Response: { patients: Patient[], totalCount: int, page: int, pageSize: int }

GET /api/patients/{id}
  Response: Patient or 404

POST /api/patients/
  Auth: Physician or Admin
  Body: CreatePatientRequest { firstName, lastName, dateOfBirth, sex, phone?,
         email?, address?, city?, state?, zipCode?, primaryProvider?,
         insuranceName?, insuranceId?, mrn? }
  Validation: sex must be M, F, or O; MRN must be unique
  Response: 201 + Patient

PUT /api/patients/{id}
  Auth: Physician or Admin
  Body: UpdatePatientRequest (all fields optional, partial update)
  Response: updated Patient or 404

DELETE /api/patients/{id}
  Auth: Admin only
  Response: 204 or 404

GET /api/patients/{id}/appointments
  Query: fromDate?, toDate?
  Response: Appointment[]

GET /api/patients/search
  Query: q (required), limit (default 10)
  Response: Patient[]

17.2 Documents — /api/documents
-------------------------------

  Response: inline file stream (Content bytes or ExtractedText as text/plain)

GET /api/documents/{id}/download
  Response: attachment download

PUT /api/documents/{id}/rename
  Body: { name: string } max 200 chars
  Response: 200 or 404

     else → seed DB from in-memory generators

Key query methods (all async, filter by PatientId):
  GetEncountersByPatientAsync, GetProblemsByPatientAsync,
  GetMedicationsByPatientAsync, GetAllergiesByPatientAsync,
  GetVitalsByPatientAsync, GetLatestVitalsByPatientAsync,
  GetLabResultsByPatientAsync, GetRecentLabResultsByPatientAsync(count),
  GetImagingByPatientAsync, GetImmunizationsByPatientAsync,
  GetNotesByPatientAsync, GetCareTeamByPatientAsync,
  GetEmergencyContactsByPatientAsync, GetInsurancesByPatientAsync,
  GetAlertsByPatientAsync, GetInteractionsByPatientAsync,
  GetRosChecklistByPatientAsync, GetPhysicalExamByPatientAsync,
  GetRiskScoresByPatientAsync, GetSmartPhrasesAsync,
  GetMedicationCatalogAsync, GetLabPanelsAsync, GetImagingCatalogAsync,
  GetInboxMessagesAsync, GetSystemSettingsAsync, GetSystemUsersAsync,
  GetLocationsAsync, GetDepartmentsAsync, GetNoteTemplatesAsync, GetOrderSetsAsync

Mutation methods:
  ReplaceProblemsForPatient(id, list) — also persists to DB
  ReplaceMedicationsForPatient(id, list)
  ReplaceAllergiesForPatient(id, list)
  PrescribeMedicationAsync, CreateLabOrderAsync, CreateImagingOrderAsync,
  CreateReferralOrderAsync, CheckOrderWarnings(patientId, medName)
